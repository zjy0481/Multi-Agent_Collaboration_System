# 多智能体协作平台初步设计

2026 年 11 月 22 日 · 团队现行设计

详细行为、验收条件和运行时接口以[首版详细需求](grill_result/agent-collaboration/requirement.md)、[领域模型](grill_result/agent-collaboration/domain-model.md)和[运行时对接设计](grill_result/agent-collaboration/runtime-contract.md)为准。

## 1. 项目目标与使用流程

用户把一个目标交给团队，成员自行决定如何拆解、谁接手、需要向用户问什么，以及如何证明工作已经完成。首版在一台主机上运行，由 Python 后端直接调用课程指定的 DeepSeek 或 HKGAI 服务，SQLite 保存协作记录，Docker 提供私有执行环境，用户通过极简网页参与。软件开发、新闻编辑和基金研究共用同一套程序，只更换成员配置和题目。[课程要求](raw/basic_requirement.md) · [官方样例说明](<../test samples/README.md>)

用户打开团队群即可发题。Lead 接住未点名的需求，成员随后通过群聊、私聊、实际工具调用和版本交接推进工作。用户随时可以补充要求、直接联系某人、引用问题作答或查看某次验收的材料。第一题完成后，用户在原群发布第二题。团队继续使用已有成员、工作分配契约、获准共享的成果和各成员自己的经验。

本文第 2 至 4 节定义角色和协作约定，第 5 节说明异步子代理和历史回合分支，第 6 至 9 节说明工程实现、评测与联调。文中的任务拆法和对话都是用来说明行为的例子，实际运行由成员根据当次需求协商。

## 2. 建组、Lead 与长期分工

过渡 agent 读取场景的成员表、成员 ID 和原始职责提示。它先识别并创建 Lead。软件组可沿用技术负责人、新闻组沿用主编、基金组沿用基金经理。名单中缺少明显领导者时，过渡 agent 创建 Lead，将原始名单和选择依据交给它，随后退出建组流程。Lead 创建其余正式角色，保留老师给定的身份和职责，并与用户建立项目的**工作分配契约**。

契约回答三个实际问题：出现某类交付时该找谁，牵头人需要从上游取得什么材料，职责重叠时该找谁协调。每名成员可以查看名单和分工，直接向合适的同伴提出委托。Lead 掌握项目进展、处理范围与优先级冲突、对外汇总并关闭总目标。用户点名的成员可直接答复，正式成员之间也可直接委派。

| 契约无法明确分配时 | Lead 如何处理 | 留下的依据 |
|---|---|---|
| 多人胜任或职责遗漏 | 按具体交付物和用途指定牵头人，保留协作者。演示用数据可由开发准备，独立验收数据可由测试准备。 | 记录裁决和理由。可指导下次分工的边界写入契约，因成员当日空闲产生的指派只记在本次任务。 |
| 缺少能力 | 检查新成员能提供何种专长、工具能力或独立复核价值，再决定增员。 | 登记新正式角色的职责、权限、与原成员的交接边界，并更新项目契约。 |
| 缺少用户决定 | 指定了解问题的成员，向用户说明可选口径及其影响。 | 用户的实际答复与原问题、任务相连，依授权共享可执行的结论。 |

**新增正式角色与调用子代理有不同的责任归属。** 团队需要长期向某人委派一类工作时，Lead 可增设正式角色。某位成员已经接下工作，只需有人帮自己复算、调查或答疑时，该成员可派出子代理，自己继续承担上游交付责任。新成员接手续作时可得到当前版本、已有判断和遗留问题。若邀请其独立复核，可先给原始主张、来源和验收范围，再对照原判断。两种交接都限于获准共享的材料。

## 3. 从提出任务到完成交付

### 3.1 自主拆解与修订

成员先说明哪项结果可独立交付、谁会使用它以及怎样检查。其他成员可以认领、补充依赖、发现重复、提出另一种拆法或拒绝。项目契约用于寻找合适的人。**委派是一项可以协商、也可以修订的约定。** 达成一致后才登记唯一负责人、发起者、输入及版本、预期产物、主审、验收条件和依赖。成员可继续委派部分工作，同时对自己的上游交付负责。并发认领通过原子更新确定实际归属。

以软件组的同级委派为例，下表中的“开发”是派发者，“测试”是执行者，Lead 负责总目标。

| 时刻 | 发生的协商 | 平台保存或通知什么 |
|---|---|---|
| 开发请测试验收看板 | 测试反提议独立核验统计值，请开发先自测日期控件。两人确认范围、记录来源和复验办法。 | 保留提议与确认引用，按最终约定登记任务。发出邀请本身不会增加已派发任务数。 |
| 两人并行工作 | 测试请助手复算一批预约记录。开发可以派助手解释数据字段，随后继续另一项工作。 | 主会话和助手各有待办和执行记录，交接输入指向具体版本。 |
| 用户澄清取消规则 | 用户要求取消记录单列。引用旧口径的开发和测试分别判断影响，改汇总与预期结果，保留仍有效的控件检查。其他成员可主动指出遗漏的影响。 | 受影响方确认同一修订，正式角色提交更新。宿主在群内 `@Lead` 说明任务、变化与新修订，并通知相关负责人和主审。 |
| 测试交付结果 | 测试发布核验明细，引用所测版本、采用的规则及实际结果。 | 提交进入待验。宿主在群内同时 `@Lead` 和开发，主审收到待验事件。Lead 同时也是派发者时只提醒一次。 |
| 主审发现缺口 | 主审指出哪一行计算违背最新口径，以及复验的期望结果。执行者在原任务上交回新版。 | 原提交、退回证据和新版分别可查。依赖旧版的下游待复核，独立通过的模块保留结论。所有必要模块通过后由 Lead 向用户交付。 |

### 3.2 成员如何选择验证方式

已知缺少哪项证据时，成员可公开指出缺口，由掌握材料的人认领。连问题本身都有争议时，可以先独立形成判断，再交换结论。例如记者和核查员分别寻找原始研究，可以发现“检测器总体准确率”与“能否判断某一份学生作业”在证据要求上的区别。双份取证耗时，适合足以改变报道结论的主张。

需要用户决定时，成员可以用具体样例提问。对于一笔预订两小时后取消的记录，展示“原定需求两小时”和“实际占用零小时”能帮助用户解释他想用图回答什么。需要验证交付能否被他人使用时，可让接收者只凭获准交付的材料重现结果。例如发布成员从指定提交启动系统，或编辑凭引用定位支撑稿件某句话的原始段落。以上方法由成员按任务选择。

**专业分歧也可以通过协商形成交付。** 研究员与风险经理可能都认可订单增长，却分别判断为持续需求和提前备货。双方可约定补查后续订单与库存变化，或共同交付两种情景以及区分它们的观察指标。记录双方接受的具体提议，报告保留各自的专业判断。若用户需要单一投资建议，由承担决策责任的基金经理说明所选假设、依据和风险。

## 4. 消息、任务状态与工具权限

网页呈现群列表、按时间排列的对话、输入框和按需展开的任务或证据详情。用户输入普通群消息就能开始，Lead 可先澄清再登记。一个群顺次推进总目标，期间的补充关联当前目标，明确另起的需求可排队。不同团队和同一目标下独立的工作可以并行。界面与后台分离，关闭网页后工作仍可推进。[交互线框](teammate/ui-prototype.html)

路由先处理对待答问题的引用，再处理明确点名的收件人，最后将真人未点名消息交给 Lead。普通群消息对全群可见，只有需要行动的角色被唤醒。进度广播写入历史。同组两个正式角色、用户与任一角色都可以用 `pair` 私聊。API、模型输入、摘要、附件、检索、回放和导出使用相同的可见范围。私聊中达成的变更只将可公开的进度写入群通知。涉及用户私密信息时，先确认可分享的业务表述。

一项工作可经历协商、已派发、等待依赖、就绪、执行中、等待真人、待验、退回返工与通过。问题有独立编号并绑定提问人、答复人和受阻任务。等待时释放执行槽。答复只解除对应阻塞，其他依赖满足后才恢复执行。拒绝授权、运行超时、预算耗尽和无法交付都保存原因。服务端检查身份、同组归属、可见范围、职责、修订和依赖环。

| 协作工具 | 谁使用，成功后发生什么 |
|---|---|
| `register_goal` | Lead 引用用户原始消息登记目标，按原消息去重。 |
| `post_message` | 按群聊、点名或私聊发送消息。明确区分可阅读者与需唤醒者。 |
| `ask_human` | 成员说明所需决定和受影响工作，立即得到问题编号。真人通过用户入口引用答复或授权。 |
| `read_state` | 按调用者身份读取任务、消息、待答项、产物和本人经验，以游标继续查询。 |
| `assign_task` | 正式角色登记已确认的委派。记录派发者、唯一负责人、主审及依赖，就绪后投递。 |
| `update_task` | 初始四个正式角色均可调用，子代理无权生效更新。对具体任务校验参与关系、承诺变化的确认记录和预期修订号。并发冲突先重读。新增正式成员的权限在建角时显式配置。成功后自动在群内通知 Lead。 |
| `publish_artifact` | 获授权者将自己工作区的内容发布为不可变版本，注明作者、所属任务和读者。 |
| `read_artifact` | 有权的接收者按版本读取内容或取得只读副本，保存交接所依据的版本。 |
| `submit_result` | 正式负责人提交当前任务修订、产物版本、验证证据和遗留问题，触发完成通知。返工重交时引用上次被退回的提交。 |
| `review_result` | 指定主审或承担验收责任的 Lead 对当前提交给出有依据的决定。退回注明原因与复验条件。 |
| `record_lesson` | 成员将决定、证据、成功或失败及适用条件写入自己的记忆。 |
| `close_goal` | Lead 核对必要模块的有效验收、未解阻塞和最终版本的可读性，再向用户交付。 |

角色提示保留原始领域职责。`team_lead`、`specialist` 和 `evidence_review` 分别提供团队推进、成员交付和按证据审查的行为说明。主审随具体任务指定。工具可见性与具体操作的授权均由宿主执行。

## 5. 异步子代理与上下文继承

### 5.1 双方都可以派出助手

每位正式成员有持久主会话、收件箱和自己的沙箱。同一主会话逐次决策，在下一次决策前读取已送达的新指示。子代理拥有独立调度的会话和受限执行空间。由此，父代理处理下一项任务时，子代理仍可完成原任务的一部分或回应交接问题。

发起方 A 可以留下一位熟悉交付背景的助手，接手方 B 也可派助手执行检查。B 或其助手可在本次委托范围内找 A 指定的联系人求证。父代理给出目标、可分享材料、执行范围和接收结果的人。助手返回依据、结果与未决问题。父代理检查采用哪些结论并承担最终交付责任，需要真人授权的动作仍走用户入口。

| 用法 | 怎样分配上下文 | 父代理如何使用结果 |
|---|---|---|
| 并行取材 | 研究员将不同公司的披露分别交给助手，要求注明原文位置、日期、币种和期间。 | 统一口径后比较，多出来的汇总和复核时间计入研究工作。 |
| 独立复算 | 只提供真实记录、日期范围和取消规则，助手先给出自己的逐笔明细。 | 与看板对照，检查数字相同的记录是否来自同样的计入规则。 |
| 持续追问 | 同一助手在同一题内阅读论文，先查样本来源，随后定位阈值、误判范围和原文段落。 | 复核具体引文，记录后续追问是否纠正了最初解释。 |
| 交接答疑 | 交付方助手持有当时版本的背景，可直接回答接收方针对该版本的疑问。 | 已有依据足以解答时父代理继续当前工作，涉及新承诺时将草案交回有权的正式成员。 |

### 5.2 从指定历史回合创建子代理分支

**会话检查点**定位父代理某个已完成回合及当时的任务修订、材料版本。**分支**从该点创建可独立延续的会话。全部历史都在授权范围内时可以继承整段对话，否则只提供本任务可用的材料。文件内容通过授权版本或快照取得。两位助手互相交换的只有本次协商中发出的消息和材料。父代理随后开展的新任务留在自己的会话，影响当前委托的修订则定向送达。

可让两名助手异步起草初次委托或修订，向各自主代理交回同一份草案、相对现行约定的变化和需要决定的事项。由承担承诺的正式角色确认后，才登记任务或更新修订。若助手基于第 3 版协商，返回时现行版本已是第 4 版，它应先核对差异、重新谈妥受影响条款。确认前继续使用现行约定，草案与讨论留作追溯。

用户已确认首版支持从指定的已完成回合创建子代理分支。检查点、按来源授权的历史继承、独立执行、同题续问及草案审查的联调条件见[运行时对接设计](grill_result/agent-collaboration/runtime-contract.md)。若多个成员反复需要直接向同一助手委派工作，可交由 Lead 判断这是否已成为团队的长期职责。

## 6. 运行时、存储与故障恢复

| 实现单元 | 负责的行为与边界 |
|---|---|
| 静态网页与 FastAPI | HTTP 接收带请求 ID 的命令，先落库再响应。群快照带事件游标，浏览器通过 SSE 接收后续可见事件。断线后按序补发、按编号去重，游标过期时重取快照。 |
| Python 模型客户端与工具循环 | 所有角色、子代理、摘要和辅助调用只访问课程指定的 DeepSeek 或 HKGAI 端点。记录角色、目标、模型和调用次数。正式模式下，配置缺失或认证失败应明确报错。显式 mock 仅用于离线回归。 |
| 调度器与协作服务 | 按收件人领取持久待办，装配可见上下文，将工具的结果按调用 ID 送回原会话。跨成员的动作由业务事件触发。模型调用、网络请求和长工具执行均在数据库事务之外。 |
| Docker、Git 与受控工具 | 正式角色各有非特权容器、私有卷、资源配额和超时。工具支持检索、数据获取、文件读写改删、编写和执行测试。独立代码修改可按需使用 Git worktree。宿主保管模型、搜索和推送凭据，关键外部动作先取得真人许可，检查 Git commit、批准的 push 目标及实际回执。 |
| SQLite 与产物存储 | SQLite 记录关系、状态变化和动作回执。文件系统保管不可变产物，接收者导入获准读取的副本。由相同记录生成群内可见的计划、对话、版本清单及评测结果。 |

群关联成员、契约、线程与消息。目标由原始消息建立，子任务关联父任务、发起者、负责人、主审、输入、用户决定及依赖。任务修订标识当时生效的承诺，产物版本标识具体字节或 Git 提交，提交将二者和证据绑定起来，审查再指向该次提交。例如，若审查人发现报道第二版中一处引文不足，第三版应关联该意见，审查人仍可打开当时审过的第二版。

**可靠性以可核对的结果为准。** 任务状态、事件和待投递收件箱在同一短事务中提交。请求重放复用原回执，同键不同内容返回冲突。修订号防止旧结果覆盖新约定。重启后从持久记录查出待答问题、待投递任务和未结运行，对照会话、工作区和已提交动作判断下一步。Git push 等外部操作超时后先核对远端目标及版本，结果仍未知时保留待核对状态。消息已送达、执行者已提交、主审已验收分别留证。

## 7. 跨题延续与个人经验

第一题结束时冻结最终产物、验收依据和已知限制。第二题使用独立的目标 ID、验收条件和起止时间。成员在原群检索获准使用的公开决定、产物目录、个人经验及其来源，再选择引用、重新调查或舍弃。群组、私聊、个人卷及经验各自沿用原来的可见范围。

一条经验应能回答“在什么条件下，下次会怎样做”。例如核查员发现二手转述遗漏了原始研究的样本限制，在下一题先查原论文，记录这次检索改变了哪句话。基金研究员可复用核对公司原始披露的方法，而上题客户的个人偏好只适用于上题。报告将记忆引用关联到实际行动、证据和结果，也记录引用后行为没有变化的情况。

## 8. 三组场景怎样验收

| 任务 | 交付与检查 |
|---|---|
| 软件 T1 · 会议室预约 | 在发布角色的干净工作区按说明启动交付版本，查询空闲、预订、尝试重叠预订、取消并再次预订。保存真实预约记录、实际结果和所测 Git 提交。 |
| 软件 T2 · 使用看板 | 从 T1 版本和记录继续，切换日期范围，逐房核对预约次数、总时长、繁忙日和时段、取消情况。按用户确认的取消及边界口径复算，在图表和摘要中找到对应结果。 |

## 9. 评测口径与首轮联调

| 指标 | 分母、起点及边界 |
|---|---|
| 子任务完成率 | 已通过验收的唯一子任务数 ÷ 已达成约定并派发的唯一子任务数。保留原始分子和分母。返工沿用同一编号，未接受草案不计入，分母为零记为不适用。 |
| 总目标完成率 | 已验收总目标数 ÷ 用户已布置总目标数。失败、超时和未完成样本保留在报告中。 |
| 端到端执行时间 | 从用户布置该目标到最终产物交付，包含等待真人的时间。另列等待区间。失败或超时记录截至终止的耗时和原因。 |

评测按权限导出带发言人和顺序的完整可见对话、输入输出版本、验收证据、运行模式、模型调用和记忆采用记录。正式成绩使用课程端点和课程闭集的真实运行。可用相同模型、工具、预算和外部验收条件对照单成员与团队执行，注明真人澄清差异，并展示一次同伴证据如何改变结果。该对照用于分析协作价值。

| 联调顺序 | 可观察的通过条件 |
|---|---|
| 1 · 模型与环境 | 连续执行两个有数据依赖的工具调用，模型在第二步实际使用前一步结果。移除课程凭据后正式模式明确失败。角色能测试自己的代码，第三人读不到私有草稿与宿主密钥。 |
| 2 · 建组与自主分工 | 分别导入有、无明显 Lead 的名单。观察真实提议、反提议、已生效委派和职责缺口裁决。首次修订契约后，下一次同类工作可按契约直接找到负责人。 |
| 3 · 消息与异步工作 | 主代理推进另一项任务时，子代理完成原任务答疑，有重叠的执行区间及各自回执。子代理直接提交正式更新被拒绝。第三个角色的查询、模型输入、回放和导出只含其获准查看的内容。 |
| 4 · 修订、真人答复与恢复 | 两个问题同时待答，重启后引用其中一个，仅相应任务恢复。重放更新与提交请求，各产生一次有效业务变更和应有的群通知。测试旧任务修订、过期草案及旧提交均无法覆盖当前版本。 |
| 5 · 版本交接与验收 | 下游凭授权取得发布版本，按约定独立复现。只退回失败模块，原负责人以同一任务提交新版，独立通过项保留，受影响项重新核查。Lead、派发者和主审各自能看到应有进度。 |
| 6 · 连续任务与报告 | 三组分别运行两题，对照第 8 节检查产物。用原始任务编号、时间和版本重算指标，追踪一次成功或失败的经验复用，并保存实际运行中的失败原因。 |

目前需要原型给出证据的环节包括课程端点的多轮工具调用、沙箱及私聊隔离、主子会话并行、检查点分支和重启对账。课程交付包括 GitHub 仓库、每位组员持续实质贡献的提交历史截图、架构文档、mid/final 性能报告与第 13 周展示。闭集的实际发放日以课程通知为准。[课程交付要求](raw/basic_requirement.md)
