步数耗尽按运行时事件计数，原回合恢复按操作者或测试运行器发起的检查点续接计数。供应商客户端自动重试计入请求，进程接续单列。请求数和事件数随运行窗口与实际工作量变化，适用于描述本次运行轨迹。

- **A 的开发和结案停滞。** 全程有 1,718 个普通消息投递回合，其中 1,645 个由前一普通消息回合发出的消息触发。应用获批前后，成功请求的输入中位数由约 26 万上升到 74 万 token，延迟中位数由 4.4 秒上升到 13.6 秒。指南于 01:50 获批，应用于 03:19 获批，三项委派累计产生 12 次正式提交和 11 次审查。05:46 的最后一份 QA 提交送达指定审查人和组内 Lead，两者均在首个模型请求收到 HTTP 400 并失败。日志没有保留 400 响应正文，其原因未知。09:06:55 之后没有新模型请求，约 90 分钟后操作者停机。队列已空且没有待答澄清时，目标仍显示 `active`。本轮两次接续同一运行库，其中一次发生在运行器异常退出后。
- **B 与 C 的半小时截止。** B 已获得应用批准，仍需完成指南与结案。C 的同一开发投递在累计第 20 步和第 40 步两次耗尽并恢复，第 48 步因单次决策的工具调用数量超过上限而失败。提高步数后仍可遇到另一项回合限制。两轮均未取得最终交付，无法对成品质量进行同口径比较。
- **D 的冻结版验收。** 两项委派均正式提交并获批。团队 QA 记录 10 项验收条件及 18 项测试通过。结案后的独立 Docker 检查从冻结文件组装应用，覆盖查询可用性、预约与重叠拒绝、取消后重新预约、重启持久化等 7 个 HTTP 场景，并重跑 18 项随附测试。容器验证约 1.749 秒。浏览器点击流程未覆盖。独立时区检查发现，UTC 浏览器在 `2026-11-24 16:30 UTC` 默认选中 `2026-11-24`，此时香港日期已是 `2026-11-25`。这轮取得了平台结案和部分独立质量证据，全面质量评估仍待完成。

## 现阶段归因

- **实测速度与队友反馈方向一致。** 本机在相同合并后基线、20 步上限、同一入库题面与 60 秒 HTTP 超时设置下，HKGAI 用约 15 分钟完成了交付，OpenCode 在 30 分钟时没有正式应用提交。队友反馈其本地 HKGAI 输出约 45 token/s，合并后平均每题不超过 20 分钟，六题均完成平台结案。不过按队友的验收口径，六题均有待补足项，均未通过验收。这是队友汇报的另一组结果，本机四轮的统计仅采用各自留存证据。
- **模型版本与质量假设。** OpenCode 配置请求 `deepseek-v4.1-flash`。HKGAI 配置请求 `t2_hkgai-v3_fp8_1m_e7`，本次成功响应统一标记为 `t2_hkgai-v3_fp8_1m_e10`。团队的待验证假设是，HKGAI 可能采用较早的 DeepSeek 版本（疑似 V4 Flash），能力或行为差异可能使任务更早收尾，交付仍留缺口。公开的 HKGAI V3 发布资料和 DeepSeek 版本记录没有确认本次 `e7` / `e10` 接口标识映射到哪个具体 DeepSeek 权重版本。当前的结案、局部验收及队友反馈不足以确认模型能力差异，也不足以确认较早结案的原因。[HKGAI V3 发布资料](https://www.info.gov.hk/gia/general/202606/03/P2026060300659.htm) · [DeepSeek 官方版本记录](https://api-docs.deepseek.com/zh-cn/updates/)
- **比较边界。** A 中大量相互触发的消息回合、不断增长的上下文和关键审查 HTTP 400 均有直接证据。B、C 在 30 分钟截止时都未结案，C 全部请求返回 HTTP 200 仍未交付。四轮中，题面业务正文相同，B 入库文本额外包含 Markdown 标题和代码围栏，C 与 D 的实际入库文本哈希一致。C 与 D 的供应商、模型配置和实际澄清内容有差异，C 启用了搜索配置、D 未启用，二者均无工作区检索记录。B 与 C 还同时改变了代码基线和步数上限。每个配置各实跑一次，现有结果无法单独估计 PR #16、步数或模型的影响，也无法判断 A 的长时间停滞出现的频率。
