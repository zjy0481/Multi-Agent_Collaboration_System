本文中的 `.tmp` 路径指原验收机器的本地记录，仓库不会包含这些文件。可按本地环境配置指南运行仓库内测试。
本轮使用 HKGAI `t2_hkgai-v3_fp8_1m_e7`、实际 Docker 沙箱和本机 SearXNG。仅重新布置上一轮未通过的五题，逐题保留官方消息原文和 SHA-256。新闻与基金各组在同一四角色团队顺序收到两道题。每题名义窗口为 20 分钟，窗口结束时若有关键任务投递在运行，或过去 45 秒内产生过新发布、提交或审查，最多追加 75 秒。操作者模拟回答澄清，并对符合条件的关键失败投递调用回合恢复接口。 [官方题目](<../../test samples/README.md>) · [上一轮记录](t015-first-fix-rerun.md)

软件组沿用隔离副本中的原团队和已通过的第一题应用 v3。上一轮没有保存原预约数据库。本轮用该 v3 启动独立 Docker 实例，从真实预约 API 写入 4 条标记记录，包括 3 条有效预约和 1 条取消，再通过 SQLite 一致性备份生成数据库。测试操作者通过正常发布工具授权读者，在单独补充消息中给出代码和快照的固定版本。这是本次重建实例的数据，软件题并未重跑第一题的 Agent 协作。相关证据位于 `.tmp/t015/official-second-fix-software-20261123/software/fixture/` 和 `handoff-fixture.json`。

首次尝试准备软件场景时，运行器把发布者也列入读者名单，发布权限校验拒绝了请求，尚未发出官方题。运行器改用 `list_workspace_readers` 返回的名单后单独启动软件场景。五题结果使用这次成功启动的看板布置。两个进程的运行时源文件 SHA-256 一致，均与最后留下的工作树实现匹配。

## 修复与回归

- 根据当前有效的上游验收计算下游状态。全部依赖满足且固定输入可读时，审查事务为负责人写入就绪投递，重放审查不会重复投递。保留任务的原修订和历史验收。 [依赖状态测试](../../tests/test_dependency_readiness.py)
- 关键回合达到步数上限时可通过原 `/retry` 从检查点续跑。默认每次增加 12 个模型步骤，累计上限 60。原工具回执继续沿用。临时超时仍沿用原恢复入口。 [恢复测试](../../tests/test_model_recovery.py)
- 搜索回执携带上游状态。`read_source` 可对当前会话搜索命中的公共 HTTPS 地址读取正文，记录原链接、读取时间和 SHA-256。`get_source` 取回已保存的证据。首版支持 HTML 和纯文本。 [证据回执测试](../../tests/test_source_evidence.py)
- 调度优先处理派工、就绪、退回和澄清等行动事件。通用提示要求先确定最小交付与共用验收口径，在输入允许时并行推进，并尽早形成可审稿或版本。

在 Python 3.14.5 环境开启 `RUN_DOCKER_TESTS=1`，完整测试结果为 **170 项通过，6 项按联调开关跳过**。JUnit 位于 `.tmp/t015-second-fix-full-1.xml`。

## 并行证据口径

运行器约每两秒记录当前目标正在执行的角色与回合 ID。报告分别核对两个以上角色同时活跃，以及两个重叠回合是否各有成功写文件、更新文件或发布产物的回执。后一项佐证同时推进了生产工作，回执本身没有提供精确到同一瞬间的文件写入时间。独立审查和正式结案仍按具体交付版本核对。

脚本模型对照单独使用同一团队的两个独立任务，按正式调度和工具路径执行。两个 Docker 工作区的执行区间重叠 **3.25 秒**，两个角色各完成写入、执行、发布和提交，共 8 个成功回执。该对照使用脚本确认委派并驱动模型，验证的是平台并行生产链。脚本和结果位于 `.tmp/t015-parallel-control/runner.py` 和 `result.json`。

## 原因归类

- **软件与工具。** 依赖联动的就绪、通知去重和步数耗尽续跑均通过回归。本轮模型没有走到新的下游依赖就绪事件，因此该链路只有受控回归证据。五笔测试操作者恢复请求都已被调度器实际领取，回合可再次遇到端点超时。同一角色一次只能推进一个回合，基金第二题的恢复请求曾等待该 Lead 的在途结案通知回合。当前正文工具会返回重定向、拒绝和 URL 未匹配的状态，合法来源跳转覆盖仍有限。看板数据快照授权和可读性均已具备，试题流程还需检查正式委派的输入是否真正绑定该快照。
- **外部服务。** 两份真实运行日志共有 64 条自动重试记录。五题记录 18 次请求重试耗尽的超时事件、4 次步数上限事件。97 次检索均报告至少一部分引擎降级，92 次有返回。原文工具成功保存 9 份来源，搜索非空和读取成功都需要结合具体主张复核。统计按本轮新记录计算，排除了看板团队复制的旧历史。
- **模型及提示词行为。** 数据已可读但看板委派漏绑数据库，在取证后继续检索而未形成可审交付，以及把厂商网页延伸成缺证据的结论，都是可以定位的执行或判断偏差。测试运行器只对选中的关键失败投递请求恢复，新闻澄清回合不在该次自动选择规则里。五题运行没有固定端点负载和来源做模型对照，因此本轮无法确定哪些偏差只有更强模型才能改善。

机器汇总位于 `.tmp/t015-second-fix-summary.json`。两批实际运行目录保存逐题 `taskN-trace.json`、`taskN-reports.json`、`taskN-active-samples.jsonl`、原文校验散列和终态。独立对照保存在 `.tmp/t015-parallel-control/result.json`。完整日志为 `.tmp/t015-second-fix-live.log` 和 `.tmp/t015-second-fix-software-live.log`。
